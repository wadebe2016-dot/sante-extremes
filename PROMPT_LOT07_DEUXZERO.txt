SECTION 1 — ISOLATION MULTI-ASSOCIATIONS
========================================

Principe : UNE BASE SQLITE PAR ASSOCIATION. Aucune requête ne peut jamais traverser
la frontière entre deux associations, même en cas de bug applicatif.

1.1 Arborescence des données
    data/
      annuaire.db                  ← annuaire global des associations
      associations/
        SDE001.db                  ← Santé des extrêmes (migration de l'actuel sde.db)
        <CODE>.db                  ← une base par association

1.2 Base annuaire.db — table `associations`
    - id INTEGER PRIMARY KEY
    - code TEXT UNIQUE NOT NULL          (6 caractères, majuscules+chiffres, ex. SDE001)
    - nom TEXT NOT NULL
    - ville TEXT
    - telephone_president TEXT NOT NULL  (format +237XXXXXXXXX)
    - date_creation DATETIME DEFAULT CURRENT_TIMESTAMP
    - statut TEXT DEFAULT 'active'       ('active' | 'suspendue')
    - fichier_db TEXT NOT NULL           (chemin relatif de la base)

    L'annuaire ne contient AUCUNE donnée métier : ni membre, ni cotisation, ni montant.

1.3 Résolution du locataire (tenant)
    - Chaque requête API porte l'en-tête `X-Association: <CODE>`
    - Un middleware `resolveAssociation` :
        · lit l'en-tête, refuse 400 si absent (sauf routes publiques listées ci-dessous)
        · cherche le code dans annuaire.db, refuse 404 si inconnu, 403 si statut='suspendue'
        · ouvre (et met en cache, max 50 connexions LRU) la base de l'association
        · expose `req.db` et `req.association` au reste de la chaîne
    - Routes SANS en-tête obligatoire : GET /health, POST /api/associations (création),
      POST /api/associations/verifier-code, et les routes de réinitialisation SMS.
    - TOUTES les routes existantes (membres, cotisations, dépenses, sanctions, trésorerie,
      exports, mesures) utilisent DÉSORMAIS `req.db` et plus jamais une base globale.
      Fais une passe exhaustive : aucune route ne doit conserver une référence à l'ancien
      singleton de connexion.

1.4 Migration de l'existant — SANS PERTE
    Écris `scripts/migrer-vers-multi.js` qui, de façon IDEMPOTENTE :
      1. crée data/annuaire.db si absente
      2. insère l'association SDE001 « Santé des extrêmes », ville Douala,
         téléphone président = celui présent dans la configuration
      3. copie data/sde.db vers data/associations/SDE001.db (copie, pas déplacement)
      4. conserve data/sde.db intact en sauvegarde
      5. vérifie et AFFICHE : nombre de membres, nombre de cotisations, total encaissé,
         total impayés — les chiffres doivent être strictement identiques à l'avant-migration
    Le script se relance sans danger et sans dupliquer quoi que ce soit.

1.5 Création d'une association depuis l'application
    POST /api/associations
      corps : { nom, ville, telephone_president, nom_president, contribution_defaut }
      actions :
        · génère un code unique de 6 caractères (3 lettres issues du nom + 3 chiffres,
          avec réessai en cas de collision)
        · crée la base data/associations/<CODE>.db avec le schéma complet à jour
        · crée le membre « président » avec son nom et son téléphone
        · génère le code président initial : 8 caractères lisibles (sans I, l, 1, O, 0)
        · renvoie { code_association, code_president, nom }
      Le code président n'est affiché QU'UNE FOIS, à cet instant précis.
      Il est stocké haché, jamais en clair.

SECTION 2 — RÔLES ET CODES GÉRÉS PAR LE PRÉSIDENT
========================================

2.1 Renommage du rôle
    Le rôle `admin` devient `président` partout : base, code, UI, exports, documentation.
    Prévois une compatibilité ascendante silencieuse : un jeton portant l'ancien rôle
    `admin` est accepté et traité comme `président`.

2.2 Sortie des codes du fichier .env
    Les codes de rôle NE SONT PLUS dans .env. Nouvelle table, dans CHAQUE base d'association :

    roles_codes
      - id INTEGER PRIMARY KEY
      - role TEXT NOT NULL             ('president','secretaire','tresorier','censeur',
                                        'intendant','competitions')
      - membre_id INTEGER              (titulaire, référence members.id, nullable)
      - libelle TEXT                   (ex. « Trésorier Junior »)
      - code_hash TEXT NOT NULL        (bcrypt ou scrypt, coût raisonnable)
      - temporaire INTEGER DEFAULT 0   (1 = code provisoire à usage unique)
      - expire_le DATETIME             (renseigné si temporaire)
      - actif INTEGER DEFAULT 1
      - cree_le DATETIME DEFAULT CURRENT_TIMESTAMP
      - derniere_utilisation DATETIME

    L'authentification compare le code présenté à tous les hachages actifs de
    l'association, en temps constant, puis met à jour derniere_utilisation.
    Le limiteur de tentatives existant (5 échecs / 15 min → 429) reste en place et
    s'applique désormais PAR ASSOCIATION.

2.3 Migration des codes actuels
    Le script de migration lit les codes présents dans le .env de SDE001, les insère
    hachés dans roles_codes avec le bon rôle et le bon titulaire, puis LES SUPPRIME du .env.
    Les codes actuellement distribués aux membres du bureau CONTINUENT DE FONCTIONNER
    à l'identique. Aucun membre du bureau ne doit être dérangé par ce lot.

2.4 Attribution d'un rôle par le président — le code définitif reste privé
    Le président seul peut :
      POST   /api/roles              { role, membre_id, libelle } → génère un CODE TEMPORAIRE
      GET    /api/roles              liste des rôles, titulaires, état (sans jamais les codes)
      DELETE /api/roles/:id          révoque un rôle
      POST   /api/roles/:id/renouveler → nouveau code temporaire

    Le CODE TEMPORAIRE :
      · 8 caractères lisibles, valable 24 heures, à USAGE UNIQUE
      · le président le transmet au collaborateur (WhatsApp, de vive voix, peu importe)
      · à la première connexion avec ce code, l'application EXIGE immédiatement le choix
        d'un code personnel (6 à 12 caractères), avant tout accès aux écrans
      · le code temporaire est alors désactivé définitivement

    CONSÉQUENCE À RESPECTER STRICTEMENT :
    le président ne connaît JAMAIS le code définitif de ses collaborateurs.
    Aucune route, aucun écran, aucun export ne permet d'afficher un code en clair.

2.5 Changement volontaire de code
    POST /api/roles/mon-code  { ancien_code, nouveau_code }
    Accessible à tout titulaire d'un rôle, pour lui-même uniquement.

SECTION 3 — RÉINITIALISATION PAR SMS
========================================

Objectif : un membre du bureau qui a perdu son code se dépanne seul, sans contacter
l'éditeur ni le président, mais sans que ce mécanisme devienne une porte d'entrée.

3.1 Numéros de téléphone
    Ajoute `members.telephone` (format +237XXXXXXXXX, validé).
    Un rôle ne peut être attribué qu'à un membre disposant d'un téléphone renseigné.

3.2 Parcours de réinitialisation d'un collaborateur
    POST /api/reinitialisation/demander   { code_association, telephone }
      · vérifie que ce téléphone correspond bien à un titulaire de rôle actif
      · envoie par SMS un code temporaire à 6 chiffres, valable 15 minutes
      · réponse volontairement neutre (ne révèle jamais si le numéro existe)
    POST /api/reinitialisation/confirmer  { code_association, telephone, code_sms, nouveau_code }
      · valide, puis remplace le code du rôle par le nouveau code choisi
      · journalise l'opération

3.3 Quotas — protection contre l'abus et contre la facture SMS
    · 3 réinitialisations par mois et par association, tous rôles confondus
    · 5 tentatives erronées de code SMS → blocage de 1 heure pour ce numéro
    · le code SMS expire en 15 minutes ; un code temporaire de rôle expire en 24 heures
    · au-delà du quota mensuel : message clair invitant à demander un nouveau code
      temporaire au président (qui, lui, n'est jamais bloqué pour cette action)
    Table `reinitialisations` dans chaque base : date, téléphone (masqué en journal :
    +237******789), rôle concerné, résultat, adresse IP.

3.4 Cas particulier : le président a perdu son code
    Il n'y a personne au-dessus de lui : la récupération exige un CONTRE-SEING.
      POST /api/reinitialisation/president  { code_association, telephone }
        · vérifie que le téléphone est bien celui du président dans l'annuaire
        · envoie un SMS aux DEUX autres titulaires de rôle les plus anciens
          (secrétaire et trésorier en priorité) : « <Nom> demande la réinitialisation
          du code président de <Association>. Répondez dans l'application pour confirmer. »
        · la demande n'aboutit QUE si DEUX titulaires confirment dans les 24 heures
      POST /api/reinitialisation/president/confirmer  (authentifié par un rôle actif)
        · enregistre une confirmation ; à la deuxième, un code temporaire est envoyé
          par SMS au président
    Table `demandes_president` : demandeur, date, confirmations, état, expiration.
    Sans deux confirmations dans les 24 heures, la demande expire silencieusement.

SECTION 4 — COUCHE D'ENVOI SMS (INFOBIP + NEXAH + JOURNAL)
========================================

4.1 Interface unique
    Crée `src/services/sms/index.js` exposant :
      envoyerSms({ destinataire, message, association })
        → { succes: bool, identifiant: string|null, erreur: string|null }
    Le fournisseur est choisi par la variable d'environnement `SMS_FOURNISSEUR`.
    Changer de routeur = modifier une ligne du .env + redémarrer le service. Rien d'autre.

4.2 Implémentation `infobip` (ACTIVE PAR DÉFAUT)
    Fichier src/services/sms/infobip.js
    Variables : INFOBIP_BASE_URL, INFOBIP_API_KEY, INFOBIP_EXPEDITEUR
    Appel POST {BASE_URL}/sms/2/text/advanced
      en-tête Authorization: App {API_KEY}
      corps : { messages: [ { destinations:[{to}], from, text } ] }
    Gère : délai d'attente 10 s, 2 réessais avec repli exponentiel, journalisation du
    messageId retourné, erreurs réseau capturées sans faire tomber le serveur.

4.3 Implémentation `nexah` (PRÊTE, NON ACTIVE)
    Fichier src/services/sms/nexah.js
    Variables : NEXAH_BASE_URL, NEXAH_UTILISATEUR, NEXAH_MOT_DE_PASSE, NEXAH_EXPEDITEUR
    Implémente l'envoi selon l'API HTTP de Nexah (user, password, senderid, mobiles, sms),
    avec la MÊME signature de fonction et le MÊME format de retour qu'Infobip.
    Si une variable manque, le module renvoie une erreur explicite sans planter le service.
    Documente dans docs/sms.md les trois lignes à changer pour basculer vers Nexah.

4.4 Implémentation `journal` (tests et recette)
    Fichier src/services/sms/journal.js — n'envoie rien, écrit le SMS dans les logs et
    renvoie un succès simulé. Utilisée quand SMS_FOURNISSEUR=journal.

4.5 Traçabilité et coût
    Table `sms_envoyes` dans annuaire.db : association, destinataire masqué, motif,
    fournisseur, identifiant, succès, date. Permet de suivre la consommation réelle.
    Ajoute GET /api/admin-produit/sms/statistiques (protégé par ADMIN_PRODUIT_CODE en .env,
    réservé à l'éditeur) : volume par association et par mois.
